# Контекст проекта: текущая схема и оставшаяся работа

Статус: 2026-10-26. Документ заменяет прежний журнал проектирования (2000+ строк
заметок). Здесь только то, что работает сейчас, чего не хватает и что сознательно
не делаем. История обсуждений осталась в git.

## 1. Задача

Агент работает в проекте долго и в разных режимах. Контекст должен:

- переживать перезапуск приложения;
- позволять продолжить работу в другом режиме (Terminal → Chat и т.п.);
- не отправлять в модель весь журнал целиком;
- не смешивать задачи разных сессий;
- не заставлять модель заново открывать правила конкретного проекта.

## 2. Три слоя памяти

| Слой | Где | Время жизни | Кто создаёт |
|---|---|---|---|
| Journal | `.logos/sessions/<id>.jsonl` | пока жива сессия | приложение, по событию |
| Session summary | рядом с сессией (целевое) | пока жива сессия | fallback сразу, LLM по порогу |
| Project baseline | `AGENTS.md` в корне проекта | пока жив проект | человек |

Journal — источник истины. Summary — его сжатие. `AGENTS.md` — стабильные правила
проекта, которые не выводятся из журнала и не перегенерируются моделью.

Разделение важно: summary отвечает «что уже сделано и что дальше», `AGENTS.md` —
«как здесь принято работать».

## 3. Как работает сейчас

### 3.1 Journal

Одна append-only JSONL-сессия: заголовок `session` (id, mode, project_root, cwd),
далее события `message`, `reasoning`, `tool_call`, `tool_result`, `job_result`,
`usage`, `error`. Вложения хранятся в `message.attachments` как ссылки с путём,
размером, SHA-256 и статусом. Секреты вычищаются до записи (`redact_value`).

Сессия привязана к одному режиму: `chat`, `terminal`, `browser`, `vision`.
Смена режима в непустой сессии создаёт новую сессию; в пустой — переписывает
заголовок.

### 3.2 Summary

Сейчас summary **один на проект**: `.logos/context/summary.md` и
`.logos/context/summary.json`. Это известный дефект (см. 5.1).

- Фиксированные секции: `Objective`, `Done`, `Current`, `Next`, `Files`,
  `Blockers`.
- Детерминированный fallback пишется при смене режима/сессии, чтобы UI не ждал
  LLM.
- LLM-обновление запускается в фоне, когда usage пересёк
  `summary_threshold_ratio` (по умолчанию 0.6) либо накопилось
  `MIN_EVENTS_FOR_SUMMARY` событий. Есть backoff 15–300 с и отдельная модель
  `context.summary_model` (`provider:model`).
- Перед отправкой старые tool-результаты обрезаются: 2k символов на tool output,
  recent tail 20k, весь prompt не больше 40k.
- Fallback доступен всегда; при ошибке LLM остаётся предыдущая версия.
- `needs_refresh` сравнивает `source_session` meta с текущим файлом и при
  несовпадении считает счётчик событий с нуля: сводка другой сессии формально
  годится как источник, но смешивается с текущей.

### 3.3 Handoff между режимами

| Переход | Что получает модель |
|---|---|
| Chat → Chat (та же сессия) | историю сообщений; summary не вставляется |
| Terminal/Browser → любая | summary проекта, если оно из другой сессии |
| Любая → Vision | summary всегда (свежая CUA-цепочка не видит журнал) |
| Resume Browser/Vision | `session_injection_block`: objective + сводка собственного журнала |
| Первый запрос сессии | summary, если есть и относится к другой сессии |

Точки: `handoff_prompt()` / `session_context_prompt()` в `src/controller.py`,
`src/context/handoff.py` (`should_inject`, `injection_block`,
`session_injection_block`). Chat получает блок как system context, Terminal и
Browser — первой записью истории, Vision — первым сообщением новой цепочки.

### 3.4 Вложения

Текст вложения не пересылается на каждом шаге. Модель получает ссылку (name,
kind, size, path, status) и читает файл инструментами `read_files` /
`list_directory` / `search_file_content`. Chat без tool-loop инлайнит текст один
раз в текущем запросе. Изображения идут провайдеру как изображения.

### 3.5 Окно контекста

`src/context/context_stats.py` считает usage из provider-reported `usage`-событий
и грубую оценку по символам. `src/context/tokens.py` хранит размеры окон.
UI: индикатор, диалог Context, кнопка `Compact now`, предупреждение на 80%.
Цены не считаются и не хранятся.

Подробно: [context_window_plan.md](./context_window_plan.md).

## 4. Что реализовано

- JSONL-журнал, восстановление последней сессии, миграция старых `session-*.json`.
- Один режим на сессию; перенос objective в заголовок.
- Summary с фиксированными секциями, deterministic fallback, LLM refresh,
  pruning, backoff, `summary_model`.
- Handoff Chat/Terminal/Browser/Vision по таблице выше.
- Контекстная статистика, `Compact now`, порог 80%, отсутствие цен.
- Вложения по ссылке; метаданные в Session journal.
- Терминал: неинтерактивный stdin, объединённый вывод, head+tail, полный файл
  вывода, inactivity timeout, фоновые задания, Stop.
- Browser: policy URL/private-network, approval gate, Stop, лимиты, refs.
- Безопасность Vision P0 (подтверждение опасных действий).
- `ruff` и `compileall` проходят.

## 5. Оставшаяся работа

### 5.1 Summary на уровне сессии (главное)

**Проблема.** Проект `shop-backend`, две независимые сессии:

- A (Terminal): «Починить тесты после миграции» — обновлён fixture, тесты зелёные.
- B (Chat): «Написать README для API».

Сейчас обе видят `.logos/context/summary.md`. Открыв B, пользователь получает
в промпте `Done: обновлён fixture...` из A. Хуже: LLM-обновление B пишет поверх
общего файла и уносит в него `Done` из A. Чем больше сессий, тем сильнее
смешиваются задачи, а объективный признак «сводка из другой сессии» перестаёт
что-либо значить: источник всегда «другая сессия».

**Целевая схема.**

- Файлы лежат рядом с журналом:
  `.logos/sessions/<session-id>.summary.md` и `.summary.json`.
- Пишет и читает только владелец сессии. `needs_refresh` сравнивает счётчик
  событий этой же сессии; кросс-сессионного слияния нет.
- При смене режима (непустая сессия) новая сессия получает **однократный seed**
  из сводки предыдущей: в её meta `source = "handoff"`, в заголовке
  `handoff_from = <старый session id>`. Дальше своя сводка живёт отдельно.
- Явное «New session» seed не получает — чистая задача.
- Resume той же сессии (Browser/Vision) использует собственную сводку, как и
  сейчас.
- Удаление сессии удаляет её summary/meta.
- Старый `.logos/context/summary.md` перестаёт читаться. Одноразовый импорт
  допустим только как seed для первой новой сессии; затем файл игнорируется.

**Что это даёт на примере.** A и B живут раздельно: B не видит fixture из A,
LLM-обновления не перетирают чужие `Done`. Если пользователь переключает A в
Chat, новая сессия один раз получает `Done`/`Next` из A — это осознанный
handoff, а не случайная утечка. Если он нажимает «New session», контекст пуст.

**Приёмка.**

- Две сессии одного проекта не видят summary друг друга.
- Смена режима даёт новую сессию с seed и `handoff_from`; повторный запрос seed
  не дублирует.
- «New session» не содержит чужих `Done`.
- Удаление сессии удаляет её summary.
- Legacy `context/summary.md` не влияет на новые сессии.

### 5.2 `AGENTS.md` как стабильный baseline

**Проблема.** Правила проекта («uv, Python 3.12», «миграции только в
`db/migrations`», «не редактировать `src/api/generated`») сейчас нигде не
читаются. Модель либо выводит их из кода, либо нарушает. Summary для этого не
годится: он меняется каждый шаг и описывает сделанное, а не правила.

**Схема.** Читается только `AGENTS.md` в корне активного проекта (не в
подкаталогах, не глобальный). Файл не генерируется и не переписывается
приложением, кэшируется по `mtime` + размеру, ограничен 32 KB, проходит
`redact_text`.

Блок вставляется во все режимы **перед** handoff и выглядит стабильно:

```text
**Project instructions (AGENTS.md):**

<содержимое>

These rules apply to all work in this project. Follow them unless the user
explicitly overrides a rule; if the request conflicts with them, say so.
```

Приоритет: системная безопасность → `AGENTS.md` → summary → текущий запрос
пользователя в части цели. Явное указание пользователя может переопределить
правило проекта, но модель должна назвать конфликт, а не молча его нарушить.
Нет файла — блока нет, ошибок нет.

**На примере.** В `shop-backend/AGENTS.md` записано: тесты запускать
`uv run pytest -q`, API лежит в `src/api/`, `src/api/generated/` не редактировать,
сообщения пользователю — по-русски. Запрос «Добавь endpoint отмены заказа»
получает этот блок в Terminal, Chat и Browser. Модель сразу кладёт код в
`src/api/`, не трогает generated и пишет ответ по-русски, не изучая проект
заново. Summary при этом говорит, что уже сделано в этой задаче, — два блока
не конфликтуют.

**Приёмка.**

- Файл в корне проекта подхватывается во всех режимах и в первом запросе сессии.
- Изменение файла подхватывается без перезапуска (кэш по mtime).
- Отсутствие файла ничего не ломает.
- Секреты в файле вычищаются.
- Handoff и `AGENTS.md` видны как два разных блока.

### 5.3 Проверка живого usage

Нормализация usage сделана, но не подтверждена на живых ответах всех
провайдеров (input/output/reasoning/cache). Нужен ручной прогон и запись
результата в `context_window_plan.md`; при расхождении — правка нормализатора,
а не оценка на глаз.

## 6. Вне scope

Сознательно не делаем в этом цикле:

- захват нативного reasoning провайдеров (Anthropic thinking, Google thought,
  OpenAI reasoning) — сейчас журналируется только структурированное поле;
- AgentEvent/plan UI и отдельная панель плана;
- Browser P2/P3 (сравнение вкладок, оркестрация, расширенный профиль);
- Vision P1 (надёжность поверх P0-безопасности);
- постоянный shell/PTY, sandbox, панель и персистентность фоновых заданий;
- стоимость токенов;
- общая оркестрация нескольких агентов;
- кэш индекса, `artifacts/`, `meta.json`, глобальная память между проектами.

## 7. Порядок работ

1. Summary на уровне сессии — устраняет смешение задач, самое заметное
   пользователю.
2. `AGENTS.md` baseline — дешёвая и полезная функция, не зависит от (1).
3. Проверка живого usage — закрывает последнюю неясность в статистике.

## 8. Принятые решения

- Journal — единственный источник истины; summary всегда производный.
- Секции summary фиксированы, свободный формат не парсится.
- Одна сессия — один режим.
- Смена модели не прерывает текущий ответ.
- Vision после перезапуска получает свежую CUA-цепочку и сводку, а не скриншоты.
- Вложения передаются ссылкой; изображения — как изображения.
- Секреты редактируются до записи в журнал и summary.
- Цены не считаются.
- Оркестрация агентов не вводится.
