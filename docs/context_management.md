# Управление контекстом: память, окно и сжатие

Статус: 2026-10-26. Документ объединяет прежние `context_handoff_plan.md` и
`context_window_plan.md`. Здесь описано, как Logos хранит память сессии, считает
заполнение контекстного окна и готовит сводку. История обсуждений осталась в git.

## 1. Задача

Агент работает в проекте долго и в разных режимах. Контекст должен:

- переживать перезапуск приложения;
- позволять продолжить работу в другом режиме (Terminal → Chat и т.п.);
- не отправлять в модель весь журнал целиком;
- не смешивать задачи разных сессий;
- не заставлять модель заново открывать правила конкретного проекта.

## 2. Три слоя памяти

| Слой | Где | Время жизни | Кто создаёт |
|---|---|---|---|
| Journal | `.logos/sessions/<name>.jsonl` | пока жива сессия | приложение, по событию |
| Session summary | `.logos/sessions/<name>.summary.md` | пока жива сессия | fallback сразу, LLM по порогу |
| Project baseline | `AGENTS.md` в корне проекта | пока жив проект | человек |

Journal — источник истины. Summary — его сжатие. `AGENTS.md` — стабильные правила
проекта, которые не выводятся из журнала и не перегенерируются моделью.

Разделение важно: summary отвечает «что уже сделано, какие решения и ограничения
действуют, что проверено и что дальше», `AGENTS.md` — «как здесь принято
работать».

## 3. Память и handoff

### 3.1 Journal

Одна append-only JSONL-сессия: заголовок `session` (id, mode, project_root, cwd),
далее события `message`, `reasoning`, `tool_call`, `tool_result`, `job_result`,
`usage`, `error`. Вложения хранятся в `message.attachments` как ссылки с путём,
размером, SHA-256 и статусом. Секреты вычищаются до записи (`redact_value`).

Сессия привязана к одному режиму: `chat`, `terminal`, `browser`, `vision`.
Смена режима в непустой сессии создаёт новую сессию; в пустой — переписывает
заголовок.

Journal — источник истины для replay и для восстановления model-facing истории.
`usage`-события участвуют в статистике, но никогда не пересылаются модели как
текст чата.

### 3.2 Summary сессии

У каждой сессии своя пара файлов рядом с журналом:
`.logos/sessions/<name>.summary.md` и `<name>.summary.json`. Сводки не
пересекаются: сессия читает и обновляет только свою.

- Фиксированные секции v2: `Objective`, `Done`, `Decisions`, `Constraints`,
  `Checks`, `Current`, `Next`, `Unfinished`, `Files`, `Blockers`. Порядок
  фиксирован, свободный формат не парсится.
- `Decisions` и `Constraints` переносятся из предыдущей версии, пока события их
  не отменяют. `Unfinished` отделяет начатую незавершённую работу от ближайшего
  шага `Next`.
- `Checks` содержит только фактически выполненные проверки. Deterministic
  fallback извлекает из journal команды `pytest`, `ruff`, `compileall`,
  build/test-команды и их статус; LLM запрещено выдумывать проверку.
- Старые summary (schema v1) читаются как есть; при следующей записи
  `normalize_summary` добавляет новые секции, а `summary.json` получает
  `schema_version: 2`.
- Детерминированный fallback пишется сразу, чтобы смена режима не ждала LLM.
- LLM-обновление запускается в фоне, когда непокрытые события превысили
  `summary_refresh_tokens` (по умолчанию 30k токенов) или usage пересёк
  `summary_threshold_ratio` (по умолчанию 0.6 окна), либо перед уходом из
  сессии (`_refresh_leaving_summary`, см. Stage 6). Захват сводки при уходе
  никогда не перезаписывает LLM-сводку deterministic fallback'ом. Есть backoff
  15–300 с и отдельная модель `context.summary_model` (`provider:model`).
- Перед отправкой старые tool-результаты обрезаются: 2k символов на tool output,
  recent tail 20k, весь prompt не больше 40k.
- Fallback доступен всегда; при ошибке LLM остаётся предыдущая версия.
- `summary.json` хранит `source_session`, `event_count`, модель и `source`
  (`llm`, `fallback`, `handoff`). Для seed при смене режима добавляются
  `handoff_from` — id предыдущей сессии — и `handoff_consumed` после первого
  запроса. После ручного сжатия добавляются `compacted_through` (id последнего
  события, покрытого сводкой), `compacted_event_count` и `compacted_at`.
  Обновление сводки сохраняет границу; сдвинуть её может только явный
  `Compact now`.
- Удаление сессии удаляет журнал, вложения и оба summary-файла.
- Старый `.logos/context/summary.md` больше не читается.

### 3.3 Handoff между режимами

| Переход | Что получает модель |
|---|---|
| Chat → Chat (та же сессия) | историю сообщений; после компакции — только хвост плюс блок сводки |
| Смена режима | новая сессия с однократным seed из сводки предыдущей |
| Terminal/Browser (та же сессия) | восстановленный журнал; после компакции — хвост плюс своя сводка |
| Любая → Vision | seed/сводку всегда: свежая CUA-цепочка не видит журнал |
| Resume Browser/Vision | `session_injection_block`: objective + сводка собственного журнала |
| New session | пустой контекст, seed не копируется |

Seed создаётся в `_prepare_session_for_mode()`: сводка предыдущей сессии
копируется в файлы новой с `source=handoff` и `handoff_from=<id>`. После первого
запроса ставится `handoff_consumed`, и блок больше не повторяется; дальнейшее
состояние даёт собственная сводка сессии. Точки: `handoff_prompt()` /
`session_context_prompt()` в `src/controller.py`, `src/context/handoff.py`
(`should_inject`, `injection_block`, `session_injection_block`). Chat получает
блок как system context, Terminal и Browser — в начале истории, Vision — первым
сообщением новой цепочки.

После компакции `handoff_prompt()` не дублирует seed: сводку вместо сжатой
части истории несёт `compaction_block()` с меткой
`**Compacted session context (mode):**`. Vision получает этот блок в
`_task_with_handoff()` первым сообщением новой CUA-цепочки.

### 3.4 Project baseline

`src/context/project_rules.py` читает только `AGENTS.md` в корне активного
проекта. Файл не генерируется приложением, кэшируется по `mtime` + размеру,
ограничен 32 KB и проходит `redact_text`.

Блок вставляется во все режимы **перед** handoff отдельным текстом:

```text
**Project instructions (AGENTS.md):**

<содержимое>

These rules apply to all work in this project. Follow them unless the user
explicitly overrides a rule; if the request conflicts with them, say so.
```

Приоритет: системная безопасность → `AGENTS.md` → summary → текущий запрос
пользователя в части цели. Явное указание пользователя может переопределить
правило проекта, но модель должна назвать конфликт, а не молча его нарушить.
Нет файла — нет блока и нет ошибки.

### 3.5 Вложения

Текст вложения не пересылается на каждом шаге. Модель получает ссылку (name,
kind, size, path, status) и читает файл инструментами `read_files` /
`list_directory` / `search_file_content`. Chat без tool-loop инлайнит текст один
раз в текущем запросе. Изображения идут провайдеру как изображения.

## 4. Окно контекста

### 4.1 Что считается

- `src/context/context_stats.py` собирает снимок по journal-событиям.
- `src/context/tokens.py` знает `context_window` модели из `models.json`
  (fallback 128k).
- Если провайдер вернул `usage`, для процента заполнения берётся **последний**
  ответ (как в opencode), а для суммарных токенов сессии — сумма всех ответов.
- Если usage нет, используется оценка **model payload**: system, history, user,
  tool schema, skills и изображения (~1000 токенов на изображение). Блок skills
  вычитается из system, поэтому компоненты не пересекаются. Это ближе к тому,
  что реально уходит провайдеру, чем текст журнала. Оценка по журналу остаётся
  отдельным диагностическим числом (`estimate_basis = model_payload|journal`).
- Провайдеры собирают нормализованный `usage` (OpenAI Responses/CUA,
  OpenRouter, Anthropic, Google, xAI, HuggingFace); он пишется в JSONL отдельным
  событием.
- Цена не считается и не показывается: только токены — фактические от
  провайдера или явно помеченная оценка.

### 4.2 Что видит пользователь

- Индикатор заполнения контекста в композере рядом с Send: процент и tooltip с
  токенами и источником (`provider-reported`, `model payload estimate`,
  `journal estimate`). Если последний ответ нёс кеш, tooltip добавляет строку
  `Last request cache`: read/write и доля cache read от prompt. Цвет: обычный,
  предупреждение с 80%, ошибка с 95%.
- Кольцо заполнения в правой панели: в заголовке рядом с процентом, в свёрнутой
  панели — под шевроном. Значение видно и тогда, когда панель узкая или
  свёрнута.
- Клик по индикатору или кольцу открывает поповер **Context window**
  (`src/ui/context_popover.py`, `Qt.Popup` над триггером, прижат к экрану):
  процент, строка `used / window tokens · source`, сегментированная полоса и
  строки `System prompt`, `System tools`, `Skills (N)`, `Messages`, `Other`.
  Кнопка **Compress context** запускает ту же ручную компакцию, что и
  `Compact now`; ссылка **Session context…** открывает полный диалог. Доли строк
  — оценки по следующему запросу, отмасштабированные к фактическому total
  провайдера (`payload_breakdown`), поэтому в сумме дают показанный процент;
  режимы без payload (Vision) показывают одну долю цвета статуса и пояснение
  вместо строк.
- Диалог **Session context**: фактическое или оценочное заполнение, лимит,
  процент, порог, счётчики, разбивка usage, состав model payload (system,
  history, user, tool schema, images), разница «вход провайдера − оценка»,
  экономия от микрокомпакции истории и граница компакции (сколько событий
  заменено сводкой и когда). Над текстом сводки — строка диагностики:
  источник (`LLM summary` с provider::model и временем обновления или
  `Fallback summary`, либо `Handed off from another session`), покрытие
  («covers N of M events»), сколько событий ещё не покрыто и состояние
  обновления (`refresh due`, `refresh running`, `up to date`,
  `refresh paused`), посчитанное по тем же порогам, что и
  `handoff.needs_refresh`.
- В диалоге usage разделён на **Latest request** (prompt с cache read/write и
  долей кеша, output, reasoning, total) и **Session totals** по всем вызовам;
  вызовы сводки показаны отдельной строкой, потому что они не входят в текущий
  контекст. Там же — состояние автосжатия с эффективным запасом места и, если
  задана, отдельная модель сводки.
- Поле **Compaction focus** в диалоге: необязательная подсказка, что сводка
  должна сохранить подробнее; она влияет только на текст сводки.
- Кнопка **Compact now**.
- Неблокирующее предупреждение при 80% — один раз на сессию.

### 4.3 Что делает сжатие

Сжатие разделено на три слоя: сводка для handoff, микрокомпакция tool-выводов и
компакция активной истории по границе.

**Сводка (`src/context/handoff.py`)** обновляет rolling-summary:

1. Старые большие `tool_result` / `job_result` подрезаются до 2k символов с
   сохранением начала, конца и статуса.
2. Последние ~20k символов (до 12k на событие) сохраняются без pruning; общий
   prompt ограничен 40k символов.
3. `needs_refresh()` использует фактический usage последнего ответа, а при его
   отсутствии — оценку по journal-тексту.
4. После ошибки LLM-сжатия действует backoff 15–300 секунд, чтобы не зацикливать
   неудачные попытки.

Это сжатие источника для сводки. Сводка используется при handoff, смене режима,
resume Browser/Vision и как замена сжатой части активной истории.

**Микрокомпакция (`src/context/model_context.py`)** готовит отдельное
model-facing представление, не меняя журнал, UI и исходные
`command_history` / `conversation_history`:

1. Baseline включён всегда для Terminal и Browser. Tool-результаты старше
   последних ~20k символов сокращаются до головы и хвоста (~2k) с маркером и
   путём полного вывода, если он есть (`[Full output saved to: ...]`,
   `Full output: ...`, `output_file`). Последние ~20k символов уходят дословно;
   самый свежий результат не режется, даже если он больше хвоста.
2. Записи не удаляются, пары command/result не разрываются — режется только
   середина старых tool-выводов. Полный текст остаётся в журнале.
3. Опциональные настройки Settings → Context (`history_keep_last_n`,
   `history_max_result_chars`, `history_dedup_snapshots`,
   `history_trim_tracebacks`) применяются поверх baseline и по умолчанию
   выключены. Блоки `AGENTS.md`, handoff, current session context и сводка после
   компакции не режутся и не сворачиваются.

**Компакция по границе.** `Compact now` обновляет сводку и записывает границу в
`summary.json`; в модель уходит хвост после границы, а вместо сжатого префикса
вставляется блок `**Compacted session context:**` со сводкой.

1. Граница хранится как id события (`compacted_through`) и число событий
   (`compacted_event_count`), поэтому переживает перезапуск. Журнал не
   переписывается: полная история остаётся в JSONL.
2. Terminal/Browser: в `command_history` вставляется маркер
   `**Session compaction boundary:**`. `_model_history_and_stats()` оставляет
   защищённые блоки, блок сводки и записи после маркера. При восстановлении
   сессии история собирается только из событий после границы.
3. Chat: `chat_model_history()` отрезает сообщения, покрытые границей, а
   `chat_context_prompt()` добавляет блок сводки. `conversation_history`
   остаётся полным — персистенция и UI ничего не теряют.
4. Ручное сжатие ждёт завершения текущего шага: стрима ответа в Chat, tool call
   или background job в Terminal/Browser. Пока ждёт, показывает сообщение и
   повторяет попытку по таймеру, поэтому пары command/result и Q/A не рвутся.
5. Если сводка уже покрывает все события и фокус не задан, граница ставится
   сразу. Иначе `Compact now` сначала форсирует LLM-обновление сводки, а затем
   применяет границу по последнему событию на момент запроса. Явный фокус
   обновляет сводку даже при полном покрытии, чтобы подсказка не потерялась.
6. При ошибке сводки граница не двигается: показывается «Compaction failed…»,
   история остаётся прежней. Следующее обновление сводки границу сохраняет.
7. Восстановление после перезапуска (`_restore_agent_history()`) пропускает
   покрытые события, но по-прежнему находит актуальные `last_user_request` и
   подпись последнего действия, а маркер ставит после защищённых блоков.
8. Диалог Session context показывает, сколько событий заменено сводкой и когда.
   Каждая применённая компакция пишется в журнал событием `compaction` (триггер,
   `covered`/`total`, источник сводки, провайдер и модель) и при перезагрузке
   сессии повторяется курсивной строкой; вкладка Session правой панели выводит
   строку COMPACTION по последнему событию, а для старых сессий — по границе из
   `summary.json`.

**Автосжатие по запасу места и мягкому лимиту.** В Chat/Terminal/Browser
контроллер сам двигает границу той же сводкой, когда контекст достиг
`auto_compact_tokens` (по умолчанию 200k — держит запросы дешёвыми даже на окнах
1M+) **или** свободного места в окне остаётся не больше буфера ответа —
`max(15% окна, 16k токенов)`, и после последней границы накопилось минимум
4 события. Условия:

1. Режим не Vision; активный шаг завершён: Chat — `IDLE` без стрима и очереди,
   Terminal/Browser — handler в `IDLE`, нет tool call и ожидания background job.
2. Нет запроса сводки в полёте, ручной компакции и активного backoff после
   ошибки; после любой компакции действует пауза 120 секунд.
3. Настройки Settings → Context: `handoff_enabled` и `auto_compact` (по
   умолчанию включено).
4. Если сводка уже покрывает все события, граница ставится сразу; иначе сначала
   обновляется сводка, затем применяется граница по последнему событию на момент
   запроса. Старт пишется в чат как «Auto-compaction started at N tokens…»,
   успех — как «Older events were compacted into the session summary
   automatically…», ошибка — «Automatic compaction failed…».
5. Границу по-прежнему двигает только контроллер: автосжатие не переписывает
   журнал и не удаляет сообщения UI. Ручной `Compact now` доступен всегда.

### 4.4 Нормализация usage по провайдерам

1. Нормализованная запись:
   ```json
   {"type":"usage","input":0,"output":0,"reasoning":0,"cache_read":0,
    "cache_write":0,"total":0,"provider":"...","model":"..."}
   ```
2. Источники:
   - OpenAI Responses: `response.usage` / событие `response.completed`;
   - OpenRouter: `stream_options.include_usage`, `usage` в чанке;
   - Anthropic: `message_start` / `message_delta.usage` (включая CUA);
   - Google: `usage_metadata` и `usage` у Interactions API (CUA);
   - xAI: protobuf `SamplingUsage` в стриме и OpenAI-совместимый `usage`
     в non-streaming;
   - HuggingFace: OpenAI-совместимый `usage`.
3. `LLMWorker` шлёт `usage_received`, контроллер пишет `usage`-событие после
   ответа; CUA-воркер шлёт usage отдельным сигналом.

### 4.5 Ограничения и риски

- Оценка по символам может заметно расходиться с токенизатором, особенно на
  изображениях и reasoning.
- Доли состава в поповере — оценки: при provider-reported total компоненты
  масштабируются к фактическому числу, поэтому отдельные проценты строк
  приблизительны, а сумма равна показанному заполнению.
- Model payload — верхняя оценка: провайдер может урезать tool schema (OpenAI
  оставляет только `payload`), а изображения считаются фиксированно.
- Провайдеры отдают usage по-разному; отсутствие поля не должно ломать ответ.
- `total` провайдера авторитетен: у OpenAI кеш входит в input, у Anthropic —
  нет, поэтому сумма частей не всегда равна `total`.
- Живая проверка нормализации на всех провайдерах ещё не закрыта (см. §7.2).

## 5. Ориентиры: как решают другие

Сжатие контекста у зрелых агентов — не одна функция, а несколько слоёв:
микрокомпакция tool-выводов, автосжатие по запасу места, структурированная
сводка с восстановлением контекста и ручной запуск. Ниже — что делает каждый
(проверено по документации и разборам, октябрь 2026).

- **opencode** ([compaction](https://opencode.ai/v2/docs/compaction/),
  [config](https://opencode.ai/v2/docs/config/)). Автосжатие включено по
  умолчанию: при приближении к лимиту история заменяется сводкой, а последние
  ~15k токенов остаются рядом (`compaction.keep.tokens = 15000`; крупный
  tool-вывод внутри этого хвоста сокращается). Буфер по умолчанию — 15% окна,
  минимум 16k (`compaction.buffer`), поэтому сжатие начинается раньше лимита.
  Сводка структурирована под передачу работы: `Objective`, `Next Move`,
  требования, решения, выполненная и активная работа, блокеры, файлы. Ручной
  запрос — `POST /api/session/<id>/compact`. Фоновая компактация
  экспериментальная: готовит сводку на 85% порога, держит её в памяти (теряется
  при перезапуске) и не применяется к сессиям меньше ~64k. Старые сообщения
  остаются в хранилище, даже когда больше не отправляются модели. В V1 было
  pruning-поведение, в V2 от него отказались в пользу сводки.
- **Claude Code** ([разбор](https://decodeclaude.com/compaction-deep-dive/),
  [промпт и восстановление](https://zane-portfolio.kiyo-n-zane.com/blog/by/developer/learn_from_claude_code_context_compaction/)).
  Три пользовательских механизма. (1) Микрокомпакция: крупные tool-результаты
  выгружаются на диск, в контексте остаются голова/хвост и ссылка, а свежие
  результаты остаются видимыми. (2) Автосжатие по запасу: триггер — свободного
  места меньше, чем нужно на ответ плюс буфер компактации; крошечные сессии не
  сжимаются, заполнение перепроверяется периодически. (3) Ручной `/compact` с
  подсказкой фокуса и проектными «Compact Instructions». Промпт требует девять
  секций: текущее состояние, цели, недавние изменения, ключевые решения,
  активная работа, ключевые файлы, выводы, важный контекст, следующий шаг.
  Сжатие идёт без инструментов и не разрывает пары tool_use/tool_result. После
  сжатия — маркер границы, сводка (~10k токенов), до пяти недавних файлов (по
  5k), skills до 25k, memory-файлы, hook-выводы и ~20 последних сообщений.
  Отдельный слой — session memory: структурированный markdown-файл сессии с
  секциями до 2k токенов; при `/compact` сохраняются минимум пять сообщений с
  текстом.
- **Anthropic API**
  ([context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing),
  [threshold compaction](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)).
  Примитивы провайдера: `clear_tool_uses` по умолчанию срабатывает после 100K
  input-токенов и оставляет 3 последних tool-использования; серверная
  компактация по умолчанию стартует на 150K (минимум 50K, beta
  `compact-2026-01-12`), умеет `pause_after_compaction` и пользовательские
  инструкции вместо стандартного промпта. Блок сводки можно кэшировать, а
  system prompt — отдельным `cache_control`, чтобы сжатие не инвалидировало его
  кэш. Memory tool вынесен в отдельный инструмент долговременной памяти.
- **Codex CLI**
  ([обзор](https://iceberglakehouse.com/posts/2026-03-context-openai-codex/)).
  При заполнении заменяет ранние ходы сводкой; ручной `/compact`; порог
  автосжатия — `model_auto_compact_token_limit` (по умолчанию значение модели).
  `/status` показывает активную модель и расход токенов, `/statusline` —
  счётчики в футере. `AGENTS.md` читается цепочкой global → project → directory
  один раз в начале запуска; устойчивые правила живут в репозитории.
- **Gemini CLI**
  ([configuration](https://geminicli.com/docs/reference/configuration/),
  [GEMINI.md](https://geminicli.com/docs/cli/gemini-md/),
  [commands](https://geminicli.com/docs/reference/commands/)). `GEMINI.md` с
  иерархией и импортами, `/memory show|reload`; `model.compressionThreshold` по
  умолчанию 0.5, `contextManagement.historyWindow.maxTokens` — 150000.
  `/compress` заменяет всю историю сводкой; `/chat save|resume` (алиас
  `/resume`) хранит чекпойнты в каталоге проекта.
- **OpenHands** ([condenser](https://docs.openhands.dev/sdk/arch/condenser)).
  Порог — 120 событий; первые 4 сохраняются дословно, середина сжимается LLM,
  целевой размер после сжатия — около 60 событий. Ручной запуск —
  `CondensationRequest`. Варианты: NoOp, LLMSummarizing, Pipeline.
- **Cline** ([auto compact](https://docs.cline.bot/features/auto-compact)). При
  приближении к лимиту суммирует и заменяет историю сводкой, показывает это
  отдельным tool call со стоимостью; чекпойнты позволяют откатиться. Для
  моделей без поддержки — обычная rule-based обрезка контекста.
- **Roo Code**
  ([condensing](https://roocodeinc.github.io/Roo-Code/features/intelligent-context-condensing/)).
  Порог — процент в настройках (по умолчанию 100%, в примерах 80%), кнопка
  `Condense Context` рядом с полосой контекста, метрики до/после и стоимость.
  Резервирует 30% окна (20% на ответ, 10% буфер); при ошибке переполнения
  обрезает контекст на 25% и повторяет запрос.
- **Qoder** (по интерфейсу приложения). В композере видно заполнение окна
  (например, 67%) и кнопка `Compress context` для ручного запуска: пользователь
  заранее понимает, когда сработает автоматика, и может сжать раньше.
- **Aider** ([repo map](https://aider.chat/docs/repomap.html)). Про композицию,
  а не про сжатие: repo map на tree-sitter с ранжированием зависимостей
  (`--map-tokens`, по умолчанию 1k) и запрос файлов моделью. Полезен как
  ориентир «что вообще попадает в промпт», а не как стратегия сжатия.
- **Общий вывод.** Надёжнее не «сжимать при 100%», а показывать заполнение
  заранее и сжимать по запасу места (примерно 60–90%), сначала выгружать
  крупные tool-выводы, сохранять недавний хвост дословно и после сжатия
  возвращать в контекст сводку, границу, недавние файлы и состояние задачи.

## 6. Что реализовано

- JSONL-журнал, восстановление последней сессии, миграция старых `session-*.json`.
- Один режим на сессию; перенос objective в заголовок.
- Summary v2 на уровне сессии: фиксированные секции (включая `Decisions`,
  `Constraints`, `Checks`, `Unfinished`), deterministic fallback с извлечением
  проверок, LLM refresh, pruning, backoff, `summary_model`; sidecar-файлы
  удаляются вместе с сессией.
- Однократный seed при смене режима (`source=handoff`, `handoff_from`);
  «New session» остаётся чистым; legacy `context/summary.md` игнорируется.
- `AGENTS.md` baseline: корень проекта, 32 KB, redaction, cache по mtime,
  инъекция во все режимы перед handoff.
- Handoff Chat/Terminal/Browser/Vision по таблице выше.
- Контекстная статистика: actual + estimate, диалог Session context,
  `Compact now`, порог 80%, отсутствие цен.
- Индикатор заполнения в композере с цветами и tooltip, кольцо в правой панели
  и поповер **Context window** с составом запроса и `Compress context`; полный
  диалог открывается ссылкой `Session context…`; фокус-подсказка для ручной
  компакции.
- Автосжатие по мягкому лимиту `auto_compact_tokens` (200k) или по запасу места
  `max(15% окна, 16k)`, минимум 4
  новых события, только Chat/Terminal/Browser и только в покое, пауза 120
  секунд, отключается в Settings → Context.
- Показ cache read/write: последняя строка tooltip и Latest request в Session
  context с долей кеша от prompt, суммарные cache-токены за сессию и отдельный
  учёт вызовов сводки.
- Нормализация usage для OpenAI, OpenRouter, Anthropic, Google, xAI, HuggingFace.
- Вложения по ссылке; метаданные в Session journal.
- Общий model-facing слой `src/context/model_context.py`: baseline
  микрокомпакция Terminal/Browser, опциональные настройки поверх неё, маркер
  границы компакции и разделение истории на сжатую часть и хвост.
- Реальная компакция активной истории: `compacted_through` /
  `compacted_event_count` / `compacted_at` в `summary.json`, маркер в
  Terminal/Browser history, хвост после границы в Chat, блок
  `Compacted session context`, восстановление с учётом границы и настоящий
  `Compact now` с ожиданием текущего шага.
- Payload accounting: состав запроса (system/history/user/tool schema/skills/
  images), выбор basis при отсутствии usage, экономия микрокомпакции в Session
  context.
- `ruff` и `compileall` проходят.

## 7. Оставшаяся работа

### 7.1 Порядок реализации

Порядок выбран по зависимостям: сначала общий слой того, что уходит в модель,
потом сводка, потом реальное удаление истории, затем UI и автоматика.

- **Stage 0 — сделано 2026-10-26.** Model-facing слой, baseline микрокомпакция
  Terminal/Browser, payload accounting, Chat-копия истории.
- **Stage 1 — сделано 2026-10-26.** Summary v2: секции `Decisions`,
  `Constraints`, `Checks`, `Unfinished`; deterministic extraction проверочных
  команд; старые v1-сводки нормализуются при записи.
- **Stage 2 — сделано 2026-10-26.** Реальное сжатие активной истории:
  `compacted_through` по id события, маркер границы, хвост после границы
  (последние ~20k символов проходят обычную микрокомпакцию), восстановление
  контекста через сводку, настоящий `Compact now`; Chat отправляет только
  хвост. Защищённые блоки остаются в начале истории.
- **Stage 3 — сделано 2026-10-26.** Индикатор заполнения в композере, автосжатие
  по запасу места, подсказка фокуса при ручном сжатии.
- **Stage 4 — сделано 2026-10-26.** Показ cache read/write (Latest request,
  Session totals, доля кеша, tooltip) и полировка диагностики: разделение
  последнего запроса и суммы сессии, отдельный учёт вызовов сводки, состояние
  автосжатия и модель сводки в Session context.
- **Stage 5 — сделано 2026-10-30.** Поповер **Context window** с составом
  следующего запроса и кнопкой `Compress context`; кольцо заполнения в правой
  панели (заголовок и свёрнутая полоса); skills считаются отдельным компонентом
  payload и отдельной строкой состава.
- **Stage 6 — сделано 2026-10-30.** Сводка больше не деградирует до fallback и
  обновляется перед уходом из сессии (`_refresh_leaving_summary`); пороги
  отвязаны от размера окна: `summary_refresh_tokens` (30k непокрытых токенов) и
  `auto_compact_tokens` (200k контекста), окно осталось вторым условием.
  Кнопки Context/Journal убраны из левого рельса, журнал открывается из
  контекстного меню сессии. Компакция пишется в журнал событием `compaction`,
  повторяется при перезагрузке и видна строкой COMPACTION в правой панели.

Кнопка и индикатор идут после Stage 2, чтобы управлять уже существующим
механизмом. Микрокомпакция не заменяет компакцию по границе.

### 7.2 Проверка живого usage

Нормализация usage сделана, но не подтверждена на живых ответах всех
провайдеров (input/output/reasoning/cache). Нужен ручной прогон и запись
результата в этот документ; при расхождении — правка нормализатора, а не оценка
на глаз.

## 8. Вне scope

- стоимость токенов;
- live-стриминг thought summaries в Chat (агентские шаги получают summary
  вместе с полным ответом); у Anthropic принудительный tool_choice не
  возвращает thinking-блок, поэтому для его structured-вызовов summary нет;
- глобальная память между проектами;
- кэш индекса и `artifacts/`.

## 9. Принятые решения

- Journal — единственный источник истины; summary всегда производный.
- Секции summary фиксированы, свободный формат не парсится.
- Summary никогда не пересекает границы сессии; перенос контекста возможен
  только явным seed при смене режима.
- `AGENTS.md` — стабильные правила проекта, а не сгенерированная моделью память.
- Одна сессия — один режим.
- Vision после перезапуска получает свежую CUA-цепочку и сводку, а не скриншоты.
- Вложения передаются ссылкой; изображения — как изображения.
- Секреты редактируются до записи в журнал и summary.
- Сжатие меняет только model-facing представление: журнал, UI и исходные
  истории остаются полными.
- Граница компакции хранится в `summary.json` как id события и переживает
  перезапуск; сдвигает её контроллер — по явному `Compact now` или
  автосжатием в покое после минимум 4 новых событий.
- Фокус ручной компакции влияет только на текст сводки, не на границу.
- Цены не считаются.
- `total` провайдера авторитетен; семантика кеша у провайдеров разная.
- Cache read/write показываются как пришли от провайдера; доля кеша считается
  только для последнего completion как `cache read / prompt`, где prompt уже
  учитывает семантику: Anthropic держит cache-токены вне `input`, OpenAI и
  OpenRouter — внутри.
- Вызовы сводки входят в сумму сессии, но не в текущий контекст, поэтому
  показываются отдельной строкой.
